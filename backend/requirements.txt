# -----------------------------------------------------------------
# Phase 2 runtime dependencies — authentication identity (Step 2)
# -----------------------------------------------------------------

# argon2-cffi — Argon2 password hashing.
# PMP §17 Security Architecture, "Authentication: Argon2 or bcrypt password
# hashing"; PMP §8 "Passwords must never be stored in plaintext".
# CHOSE Argon2 over bcrypt: Argon2 is memory-hard, so a stolen hash table is
# expensive to attack offline — this is why the winner of the Password
# Hashing Competition is the modern recommendation, and why `users.
# password_hash` was sized at 255 characters in Phase 2 Step 1 specifically to
# hold an Argon2 PHC string (~95-100 characters).
# CHOSE argon2-cffi over passlib: passlib's last release was 2020 and its
# Argon2 support requires an out-of-tree plugin, so "argon2 via passlib" is
# strictly more moving parts for a less maintained wrapper. argon2-cffi is
# the reference binding, actively maintained (25.1.0), MIT, and its API is
# three functions. bcrypt is deliberately NOT also installed: two hashing
# libraries in one project means two implementation paths and a real risk of
# an unverified password being compared with the wrong one.
# Requires argon2-cffi-bindings (transitive, cp310-abi3 wheels cover 3.12).
argon2-cffi==25.1.0

# PyJWT — JWT creation and verification.
# PMP §17 "Short-lived JWT access tokens"; PMP §8 "JWT access tokens must
# have short expiration times"; PMP §14 refresh_tokens.
# CHOSE PyJWT over python-jose: PyJWT is the actively maintained reference
# implementation and, critically, its `decode` takes the accepted algorithms
# as a required server-side argument rather than reading `alg` from the
# token — that is exactly the "alg: none" / algorithm-confusion defence
# Phase 2 Step 2 has to prove. python-jose has a history of algorithm-
# negotiation defects and is not maintained to the same standard.
# CHOSE PyJWT over fastapi-users / authlib: those are whole user-management
# frameworks. PMP §15's /auth/* endpoints and this project's tenant-scoped
# identity model need a signing primitive, not a framework; pulling one in
# would implement the user-invitation surface that is explicitly out of
# scope for this step.
# No runtime dependencies on CPython 3.12: `typing_extensions` is required
# only for Python < 3.11, and `cryptography` only under the unused [crypto]
# extra. HS256 is a stdlib-hmac computation, so no crypto dependency is
# needed at all.
PyJWT==2.15.1

# Phase 2.5 runtime dependencies — RAG foundation
# -----------------------------------------------------------------
#
# Three packages, each with a named requirement in the PMP. Nothing from
# the deferred list below was installed "just in case": the reranker,
# BM25, Redis, Celery and the LLM SDKs all belong to phases that have not
# started, and a vector store that cannot be exercised is not a

# pypdf — PDF text extraction.
# PMP §18's ingestion pipeline begins at "Parser"; PMP §2's document
# domain (handbooks, HR policies, SOPs, compliance documents) is
# overwhelmingly PDF, and Phase 2.4 accepts `application/pdf` uploads.
# There is no standard-library option: PDF's text operators live inside a
# cross-reference table behind a font encoding, and reimplementing that
# would be a parser with no test corpus.
# Pure Python, no runtime dependencies of its own.
pypdf==6.19.0

# python-docx — DOCX text extraction.
# Same argument for `.docx`, which is the other dominant enterprise
# format. Chosen over hand-rolling `word/document.xml` parsing because
# this format's paragraph and table structure is fiddly enough that a
# home-grown reader is a source of silently-dropped content, and silently
# dropped content is a retrieval bug nobody notices.
# Requires lxml (transitive; manylinux wheels cover 3.12).
python-docx==1.2.0

# qdrant-client — the Qdrant vector store client.
# PMP §23 technology stack (Vector Database: Qdrant); PMP §13 specifies
# one collection per tenant with a documented point payload; PMP §22
# Phase 4 lists "Qdrant" as a deliverable.
# CHOSE the official client over hand-written REST calls against Qdrant's
# HTTP API: the client's request/response models are the API's contract,
# it retries and re-connects, and its `local` mode gives the unit tests a
# real engine to exercise without a server. The alternative is ~200 lines
# of untyped JSON assembly re-implemented on every Qdrant upgrade.
# Pulls grpcio, protobuf, portalocker, httpx[http2] (h2/hpack/hyperframe)
# and numpy — the gRPC transport and the in-process local mode. That
# footprint is the price of the official client and is accepted
# deliberately; it is called out here rather than discovered later.
qdrant-client==1.19.1

celery==5.6.3

# PMP §22 Phase 5 deliverable "Redis"; §19 names Redis for query

# dependency ledger previously said the decision was "settled when the
# embedding layer is built". It is now settled: this phase implements the

# and nothing in the ingestion pipeline changes.

# Four selection notes:
#
# 1. fastapi 0.142.x declares opentelemetry-api as a HARD dependency.
#    That is a genuine change in recent FastAPI releases, not an
#    error, and opentelemetry-api itself has no further dependencies.
#    It is accepted deliberately rather than by pinning an older
#    FastAPI, because downgrading would be avoiding a current stable
#    release over a transitive package that is small and widely used.
# 2. mypy 2.3.1 is a MAJOR version bump over the long-lived 1.x line
#    and adds two new dependencies (ast-serialize, librt) in place of
#    the older mypyc-compiled build. It is a stable release and is
#    used here, but the CI type-check gate is the place where any
#    behaviour change would surface first.
# 3. SQLAlchemy 2.0.54 was chosen over the newer 2.1.1 (published days
#    before this pin). 2.0.x is the mature, widely-deployed 2.x line
#    and exposes the complete 2.x API this project uses. greenlet is
#    pulled in as a hard requirement of 2.0.x on common platforms, but
#    is not used by the synchronous engine built in Step 4; it exists
#    for the asyncio support this phase deliberately does not adopt.
#    Revisit if the async stack is ever introduced.
# 4. argon2-cffi 25.1.0 resolves argon2-cffi-bindings 26.1.0, which
#    publishes a cp310-abi3 wheel. The abi3 tag is why ONE binary wheel
#    covers CPython 3.10, 3.11, 3.12 and 3.13 rather than needing a
#    per-interpreter build; `cffi` is its single runtime dependency and
#    also ships a manylinux wheel, so no compiler is needed anywhere in
#    this chain. The Python-level argon2-cffi distribution is pure Python.
# 5. PyJWT 2.15.1 adds nothing on 3.12. Its declared dependency on
#    typing_extensions is conditional on Python < 3.11 and is therefore
#    not installed here; its `cryptography` dependency is under the
#    `[crypto]` extra, which this project does not use because HS256 is
#    an HMAC-SHA256 computation and HMAC is in the standard library.
#    A deliberate zero-dependency addition.
# 6. qdrant-client 1.19.1 is the only Phase 2.5 dependency with a large
#    transitive footprint: numpy (16.7 MB wheel) and grpcio (5 MB) arrive
#    with it. numpy backs the client's in-process `local` mode; grpcio
#    backs the gRPC transport, which this project does not use — Qdrant
#    is reached over HTTP/REST, so the protobuf transport is paid for
#    and not used. Neither is removable while the official client is the
#    client, which is why the alternative (hand-written REST calls) was
#    weighed rather than assumed, and why the footprint is recorded here
#    instead of being discovered at the next install.
# 7. celery 5.6.3 is the newest release of the 5.x line. The next major,
#    Celery 6, is deliberately not taken: it flips the default of
#    `broker_connection_retry_on_startup` to False, which changes how a
#    worker behaves when its broker is not yet listening — a behaviour
#    Phase 5 Steps 2+ will have to reason about on purpose, and
#    `celery.contrib.testing.worker` is only exercised against 5.x here.
#    Recorded so the constraint is visible before somebody upgrades and
#    wonders why workers stopped waiting for Redis.
# 8. redis-py 6.4.0 is two majors behind the newest release, and not by
#    choice: kombu 5.6.x caps it at `<6.5`, which is what makes redis-py
#    7.x and 8.x uninstallable alongside Celery at all. 6.4.0 is the
#    newest version this project *can* use. It also moves one existing
#    transitive pin: `tzdata`, previously resolved to 2026.2 by psycopg,
#    goes to 2026.5 because kombu requires it too. Both constraints are
#    open-ended, so neither is a direct pin; the resolution simply moves.
# 9. Fourteen new packages arrive with celery and redis-py, and none is
#    avoidable while Celery is the task queue. amqp and vine are kombu's
#    transport layer; billiard is Celery's process pool; click-didyoumean,
#    click-plugins, click-repl, prompt_toolkit and wcwidth belong to the
#    `celery` CLI; python-dateutil and six are kombu's metadata handling;
#    tzlocal and tzdata are Celery's timezone support. prompt_toolkit is the
#    largest at roughly 500 KB and is used only by the `celery inspect`
#    shell.
#
# Packages present only to satisfy Python < 3.11 (correctly absent on
# 3.12): exceptiongroup, tomli, backports-asyncio-runner.
